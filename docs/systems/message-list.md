# Message List & Auto-Scroll

The chat message list (`packages/web/src/components/chat/MessageList.tsx`) is responsible for rendering the message stream, holding the view to one anchor (following new content, a reading position, a jump target, the first unread message), dispatching jump-to-message scrolls (search results and reply previews), marking the channel read, and triggering load-more pagination at the top.

| File | Responsibility |
|---|---|

| `packages/web/src/components/chat/scrollAnchor.ts` | `ScrollAnchor`, `resolveOpenTarget`, `firstUnreadMessageId`, `pageReachesReadPosition`: the pure parts of the anchoring model. |
| `packages/web/src/stores/chatStore.ts` | `messages`, `hasMore`, `loadStates` (per channel: loading or failed with its error), `scrollPositions` (saved anchors, in memory, session-scoped), `readStates`, `detachedChannels` (detached windows and the live messages held for each), `presentReturns`; `loadMoreMessages` and `loadNewerMessages` page backward and forward. |

## Bottom clearance — `--composer-clearance`

The MessageList content's `paddingBottom` is dynamic — it reads the CSS variable `var(--composer-clearance, 80px)` written to the chat region's wrapper element by `MessageInput` via a `ResizeObserver`. The variable's value is `composer.height + composer.bottom-offset + 12 px` so the last message always lands 12 px above the composer's top edge regardless of (a) composer height (reply banner, staged-attachment tile row, multi-line autosize), (b) the composer's own `bottom` style (desktop 12 px / mobile-keyboard-closed `env(safe-area-inset-bottom) + 6` / mobile-keyboard-open 0).

The 80 px fallback is sized for the desktop case during the brief mount window before the first measurement — it matches the previous static `pb-20`.

**The variable is never removed while the composer is mounted.** Its observers live as long as the composer element; changes that move the composer without resizing it (keyboard, focus, reply banner, staged files) only trigger a re-measure, and the value is written only when it changes. A removal followed by a measurement forces a layout at the 80 px fallback, the browser clamps the list's scroll offset to the smaller range, and when the value comes back the newest messages sit under the composer (issue #361: leaving the window blurs the textarea, which used to re-run the effect). The list observes its content through the border box, which is where this padding shows (see "Anchoring model"). See `docs/systems/mobile-ui.md` "Floating Composer" for the full rationale; the short version is that any static value is wrong on iPhone (composer height + safe-area + 6 already exceeds 80 px) and wrong when the composer grows (replies, attachments).

## ContainerRef invariant

`containerRef.current` (and `contentRef.current`) MUST be non-null for the entire lifetime of any chat view where messages may arrive or scroll-affecting effects can run. Every effect in this file (the open and rows-changed layout effects, the ResizeObserver, the capture-phase load handler, the scrollend final pin, jump-to-message) reads these refs and bails on a null guard. The observer effects are keyed on `[hasMessages, channelId]`, and the inbound transition (`false → true`) is the *only* re-fire signal during a channel-load lifecycle. If a ref is null at the moment that signal fires, the effect bails — and no later dep change will retry it, leaving the channel permanently broken (initial scroll never lands at bottom, ResizeObserver never observes, scrollend never registers, saved-anchor restore never happens).

**Implication for loading UI:** the initial-load skeleton is rendered as an absolutely-positioned overlay on top of the scroll container, NOT as an early return that replaces it. See `MessageList.tsx` (the `showInitialSkeleton` overlay block) for the canonical pattern. Any future loading/empty/error UI added to this component must follow the same rule — overlay, never replace — or the scroll model breaks under slow loads where the skeleton is visible at the moment messages arrive.

## Top-of-list reservation slot

When `hasMore === true` for the current channel, a constant-height div is rendered as the first child of the scroll container, above the messages container that holds `contentRef`. This slot exists for the entire `hasMore === true` lifetime of the channel view and its height NEVER changes. The pagination skeleton's grey-bar contents toggle inside the slot based on `showPaginationSkeleton`; the slot itself does not mount or unmount with the skeleton. This is the entire mechanism that eliminates the layout-shift bug where the skeleton's appearance pushed message content down and its disappearance snapped it back up — by keeping slot height invariant, no DOM height ever changes from the skeleton's lifecycle.

**The constant `PAGINATION_SLOT_HEIGHT_PX`** (defined at module scope in `MessageList.tsx`) is the single source of truth for three values: the slot's inline `height` style, the skeleton's structural total height (the markup is tuned so it fits comfortably inside the constant — the last row's `mb-5` is stripped to give a buffer), and the load-more trigger threshold (`scrollTop < PAGINATION_SLOT_HEIGHT_PX + 50`). It is a TS constant rather than a CSS variable to avoid a `getComputedStyle` round-trip when the threshold computation reads it back. If the skeleton markup changes (different row count, different padding, different bar height), re-measure `getBoundingClientRect().height` in DevTools and update the constant — round UP to the nearest 4-pixel step.

**Slot ↔ WelcomeHeader transition.** The slot and `WelcomeHeader` are two separate components and are mutually exclusive: slot when `hasMore`, WelcomeHeader when `!hasMore`. On the final page load that flips `hasMore` to false, the slot unmounts and WelcomeHeader mounts in its tree position. The (WelcomeHeader_height − slot_height) delta is absorbed by the anchor, which holds the row the user was reading at its offset across the prepend, so no special transition handling is required. Keeping the two as separate components is a deliberate clarity choice: each component is unaware of the other and the formula handles the join.

**Why not `overflow-anchor`.** CSS scroll-anchoring (`overflow-anchor: auto`, the default in modern browsers) is not the mechanism in use here. It cannot help: the browser's anchor-pick algorithm requires a stable element ABOVE the changing content in the viewport, and at `scrollTop ≈ 0` the slot is the topmost in-viewport element AND the one whose contents change — no stable anchor to pick. Additionally, iOS Safari (until 17) had no support, and historical edge cases interact with rubber-band overscroll at the top. The list's own anchor (see "Anchoring model"), re-applied before paint when the rows change, is the reliable path.

## Anchoring model

The list holds its view to one anchor, `anchorRef` (`ScrollAnchor` in `scrollAnchor.ts`):

- `{ kind: 'bottom' }`: the view follows the newest message.
- `{ kind: 'message', messageId, offsetPx }`: the row with that id is held `offsetPx` layout pixels below the scroll viewport's top edge (negative when it starts above it).

`applyAnchor()` puts the view back on the anchor (bottom: `scrollTop = scrollHeight`; message: shift `scrollTop` by the row's offset error) and records the offset and the scroll geometry (`scrollHeight`, `clientHeight`) it applied against. It writes `scrollTop` only when the view is off the anchor, and it leaves a jump's smooth scroll alone while the `'message'` intent is active. Every path that moves the list goes through it:

| Path | What happens |
|---|---|
| Open (channel switch or mount) | The channel layout effect resolves the open target (`resolveOpenTarget`): a saved message anchor, else the first unread message, else the bottom. It is taken once the channel's rows are rendered (`openChannel`). Until then nothing derives or applies an anchor, so the browser's clamp events from the previous channel are ignored. |
| Rows change | A layout effect on the rendered rows. New rows below a view at the bottom are followed with a smooth scroll (`'bottom'` intent). Anything else (older rows loaded above, a cache replaced under the open view, a jump's window) is re-anchored before paint. This replaces the old prepend compensation. |
| Anchored row missing | If the anchored id lies outside the oldest and newest loaded ids, it was dropped with the cache (a reconnect's reload, Jump to Present after a newer jump): `restoreAnchor` loads the window around it with `loadMessagesAround` and holds it again, or takes the view as it is if that fails. Inside the loaded range it was deleted: the anchor is taken from the layout. |
| Size change | A `ResizeObserver` on the content with `box: 'border-box'` (the composer clearance is the content's bottom padding, invisible to the content box) and on the scroll viewport (mobile keyboard, window resize), plus a capture-phase `load` listener for media. Each re-applies the anchor. |
| Jump, Jump to Present | Set the anchor first (see "Jump to message"), then scroll. |
| Close (channel switch or unmount) | The anchor is saved to `chatStore.scrollPositions` (see "Position memory"). |

**User scrolls move the anchor.** `handleScroll` treats an event as the list's own, or as caused by layout, when the offset equals the one it last applied or the scroll geometry changed since it last measured (the browser clamping the offset after content shrank); it re-applies the anchor and returns. Anything else is the user: the anchor becomes the bottom within 150 px (`AT_BOTTOM_THRESHOLD_PX`) of it, otherwise the topmost visible row with a server id and its offset. While a `'bottom'` smooth scroll we started is animating, the anchor stays at the bottom unless the user has wheeled more than 5000 px away. `isNearBottom` (within 5000 px) only decides whether Jump to Present shows.

Manual regression check for the size paths: open a conversation with enough messages to scroll, go to the bottom, then type a multi-line draft, start a reply, attach a file, switch to another window and back, and on a phone open and dismiss the soft keyboard. The newest message stays above the composer throughout. Repeat while reading older messages: the reading position holds. `MessageList.anchor.test.tsx`, `MessageList.jump.test.tsx` (viewport resizing) and `MessageInput.clearance.test.tsx` cover these with simulated geometry.

**Limit.** A layout change that is undone inside one task (remove a style, force a layout, restore it) clamps the offset and then fires a scroll event with the geometry already restored. The list cannot tell that event from a user scroll. Code that sizes the list must change its values in place, never remove and re-add them; the composer clearance is the case that did (issue #361).

**Marking read.** The channel is acked 200 ms after the anchor is the bottom and the cache is not a detached window (`chatStore.ackChannel`). `ackChannel` only sends an id newer than the local read position and does nothing for a detached channel; `onChannelAck` ignores an echo older than the local read position. Read positions only move forward, except through Mark Unread.

## Opening at the first unread message

The open target is resolved when the channel opens, from a snapshot of `readStates` taken before anything acks:

1. A reading position saved earlier in this session (a message anchor) wins.
2. Otherwise, with a read state: if the loaded page reaches the read message (`pageReachesReadPosition`: the page starts at or before it, or there is nothing older), the first unread message is the first row after it, in display order, that the viewer did not write (`firstUnreadMessageId`, own messages by `isSelf`). If the page does not reach it, `loadMessagesAround(lastReadId)` loads the window around the read message and the first unread message is found there; a window that stops short of the newest message pages forward as the user reads (see "Detached windows"). If the read message is gone or the load fails, the channel opens at the newest message.
3. No read state, or nothing unread: the newest message.

The first unread row is held 64 px (`UNREAD_ROW_OFFSET_PX`) below the viewport top, with a divider above it (`UnreadDivider`: a pastel rose rule and a "New" pill, `role="separator"` named `chat:list.unread.divider`; when the first unread message also starts a new day, the date sits inside the same rule instead of a second divider). The workbench `dev-message-list.html` renders these states. If everything unread fits on screen the view is at the bottom anyway, so the anchor becomes the bottom: the list keeps following and the channel is marked read. The divider is a snapshot for the visit; acking does not move it, Mark Unread on a message of the open channel moves it to the first unread message after that one.

Federation: the read state, the message ids and the around-query all come from the channel's origin (`getChannelOrigin`), so a federated channel and a DM pinned to another instance compare ids of one instance. A peer without the around endpoint answers 404, which opens at the newest message.

## Load failures

`chatStore.loadStates` holds, per channel, `{ status: 'loading' }` while `loadMessages` is in flight and `{ status: 'failed', error }` after it failed; no entry means idle. The initial skeleton shows for the channel's own `loading` state. A `failed` channel with no messages shows `LoadFailedNotice` (`role="alert"`, `chat:list.loadFailed`, the reason from `describeError`, and a Try again button that calls `loadMessages(channelId, true)`), as an overlay over the scroll container per the ContainerRef invariant.

## Smooth-scroll intent

Bottom-bound smooth scrolls (new-message arrival, Jump-to-Present click) and jump-to-message smooth scrolls (search result click — animates to a non-bottom target) both run `scrollIntoView({behavior:'smooth'})`, which animates `scrollTop` over many frames. Each intermediate frame fires `handleScroll` with a measured `distanceFromBottom` that does *not* match the smooth animation's terminal frame. Without intent tracking, those intermediate measurements would move the anchor off the bottom, so media (avatars, embeds, attachment images, Spotify thumbs) that finishes loading mid-animation would not be followed and the smooth scroll would land at its originally computed (now stale) target, above the true bottom.

The intent is a typed ref:

| Field | Type | Set by |
|---|---|---|
| `smoothScrollIntentRef` | `'bottom' \| 'message' \| null` | `beginSmoothScrollIntent(intent, label)` |
| `smoothScrollDeadlineRef` | `number` (`performance.now()` ms) | `beginSmoothScrollIntent` (`now + 800`) |

Behavior by intent:

- **`'bottom'`**: `handleScroll` keeps the anchor at the bottom while the deadline hasn't elapsed and the user hasn't wheeled away past 5000px (`SMOOTH_SCROLL_USER_INTENT_THRESHOLD`). The `scrollend` listener fires the final pin (or its timeout fallback). Set by: the new-message smooth scroll, Jump to Present on an attached channel.
- **`'message'`**: the jump's anchor is already set from its destination. `applyAnchor` does nothing until the animation lands, so a resize mid-animation does not cut it short; `scrollend` (or the timeout) clears the intent. Set by: `scrollToRenderedMessage`.

The 5000px user-intent threshold matches the `nearBottom` band: distances larger than that signal a deliberate user gesture (mouse-wheel away mid-animation), and we let the gate flip honestly so the smooth scroll's terminal frames don't fight the user.

## Jump to message

Every jump goes through one function, `jumpToMessage(messageId)` in `MessageList.tsx`, with an id on the channel's origin. Two entry points feed it:

- **Search results**: `MainContent` passes `jumpToMessageId`; an effect takes each request once (`handledJumpRequestRef`, so a parent that re-renders before clearing it, or passes a new `onJumpHandled` each render, does not start the load again), calls `onJumpHandled` and jumps.
- **Reply previews**: `MessageList` provides `MessageJumpContext`; `Message.tsx` renders the preview as a `<button>` that calls it with `message.replyTo.id`. Outside a list (no context) the preview is inert. The preview holds no interactive content of its own: mentions in it render through `InlineMessageText` as `MentionBadge` with `interactive={false}` (same look, plain text, no profile click), so a click anywhere on the preview jumps.

Order of work:

1. The target is in the cache and rendered: scroll and flash, done.
2. Otherwise `chatStore.loadMessagesAround` loads the window around it on the channel's origin. It returns `'loaded' | 'not_found' | 'failed'`.
3. On `'loaded'`, two frames later the target is looked up again and scrolled to.
4. Anything else leaves the view where it was and shows an info toast: `chat:list.jump.unavailable` (the message is gone, or the origin never had that id) or `chat:list.jump.failed`.

The scroll is `scrollIntoView({ behavior: 'smooth', block: 'center' })` under the `'message'` intent, and the row gets `.message-jump-highlight` (a 2 s primary-tint background fade, `message-jump-flash` in `globals.css`), removed on its own `animationend` and restartable when the same row is jumped to again. Keyboard focus moves to the row (`focusJumpTarget`: `tabindex="-1"` for as long as it holds focus, removed on blur, `focus({ preventScroll: true })` so the smooth scroll is not cut short), so the next Tab continues from the target rather than from a preview that may be off screen. It does so only if focus is still where it was when the jump started (or on `body`): a jump that waited on the network leaves alone a composer the user clicked into meanwhile. The row shows its ring only under `:focus-visible`, so a mouse-driven jump draws none. `jumpSeqRef` makes the newest request that moves the view on purpose (a jump, Jump to Present, a restore, opening at the first unread window) cancel an older one still waiting on its load, and the channel is re-checked after every await.

**The anchor is set before anything moves.** `cancelBottomPinning` forgets the list's last applied offset and cancels a pending `'bottom'` intent. Then:

- Before `loadMessagesAround` replaces the cache, the anchor becomes the target row (centred estimate) and `anchorLoadInFlightRef` is set, so the window lays out around the target instead of being followed to its bottom, and the missing target row does not start a restore.
- At the scroll itself, `centredScrollTop` computes the clamped offset of a centred row, and the anchor is set from that destination: the bottom when it is within 150 px of it (a jump to a row already on screen near the bottom may not move the list, and no scroll event follows, so the list keeps following), otherwise the row at its destination offset (messages that arrive afterwards do not pull the view back).

A jump that ends without scrolling takes the anchor from the layout (`deriveAnchorFromLayout`). A jump is also where a channel opens if it has not opened yet.

**Detached windows.** `loadMessagesAround` replaces the cache with a window. When that window stops short of the newest message (fewer than `limit / 2` messages after the target means the server ran out of newer rows; `MESSAGES_AROUND_LIMIT` is 50 and sent explicitly), the channel goes into `chatStore.detachedChannels`. Every path that loads a window lands here: a jump, opening at the first unread message (`openAtUnreadWindow`), and `restoreAnchor`. A detached window:

- **Pages forward.** When less than `NEWER_PAGE_TRIGGER_PX` (250 px, the mirror of the load-more trigger at the top) of the window is left below the view, after a user scroll or whenever the anchor is applied, `chatStore.loadNewerMessages` asks the channel's origin (`getApiForOrigin(getChannelOrigin(id))`, `channels.messagesAfter` / `dm.messagesAfter`) for the page after the window's greatest id and appends it; the contract is api.md, "Message history paging". The anchor holds the row being read, so the view does not move. One page is asked for at a time. A page shorter than the limit reached the newest message and attaches the window; a view then within 150 px of the end takes the bottom anchor. A page whose window was replaced while it loaded (Jump to Present, a newer jump, a reload, eviction) is dropped. A page that arrives after the user switched channels still extends its own channel's window.
- **Has no bottom anchor.** The bottom anchor follows the newest message, and the end of a detached window is not the newest message. A user scroll, a jump or the unread open that ends there holds a row instead, so the next page appends below without moving the view, nothing is marked read, and Jump to Present stays shown.
- **Holds live messages back.** A live message for a detached channel is not appended after the window, where it would sit after a gap with no sign of it. It is held with the channel's entry in `detachedChannels` (edits, deletions and reactions apply to it there) and still reaches notifications and sounds. When a page reaches the present (a short forward page, the newest page, a window around a recent message), the held messages newer than everything in it are appended, which covers a message that arrived while the last page was on its way.
- **Jump to Present** sets the bottom anchor and reloads the newest page (`loadMessages(channelId, true)`, which attaches the window), then pins to the bottom unless a newer jump started meanwhile. `loadMessages` resolves false when the page could not be loaded; Jump to Present then does not pin to the window's bottom (which is not the present), takes the anchor from the layout, and shows the info toast `chat:list.jump.presentFailed`. A non-detached channel keeps the plain smooth scroll.
- **Returns to the present by itself** in two cases. `chatStore` replaces the window with the newest page and increments `presentReturns`; the open list sees the change with the new rows, takes the bottom anchor and cancels any jump or restore still loading.
  - A message sent from the window (`chatStore.sendMessage`, and the attachment path in `MessageInput`) will appear at the newest end, so `returnToPresent` loads it. The optimistic message is carried into the newest page until its own message arrives.
  - An origin that predates forward paging ignores `after` and answers with its newest page, without `X-Backspace-Paging`. `loadNewerMessages` applies that page as the newest page; it is never spliced after the window.

## Position memory

- **Storage:** `chatStore.scrollPositions: Map<channelId, ScrollAnchor>`, in-memory Zustand state. The bottom is stored explicitly.
- **Commit:** the channel layout effect's cleanup saves the anchor of the channel being closed, on a channel switch and on unmount (a remount without a switch, e.g. starting a DM call or visiting Explore and back, comes back to it).
- **Use:** a saved message anchor is the open target on the next visit; its row is restored with `loadMessagesAround` if the cache no longer holds it. A saved bottom yields to the first unread message.
- **Lifetime:** session-only. Lost on reload, app restart, tab close. Across sessions the server's read state decides where a channel opens.
- **Eviction:** scroll positions are evicted alongside messages when `MAX_CACHED_CHANNELS` (`chatStore.ts`) is exceeded.

## Reconnects and refresh readies

The WebSocket `ready` handler clears the message cache of the origin's channels and force-reloads the open channel only on the first `ready` of a socket, home or remote, which may follow a gap in which messages were missed. A later `ready` on the same socket is a state refresh (instances up to 1.7.0 send one to every member as a permission refresh after role changes) and leaves the cache and the open view alone (`useWebSocket.ts`, `readyDelivered` in `connectToOrigin`); a remote instance's refresh still reloads the open space's details. After a real reconnect the open view keeps its anchor through the rows-changed path above.

## Embed renderer contract

Every renderer that contains an image, iframe, or video MUST reserve dimensions when they are known. The reference pattern is `AttachmentRenderer.tsx:81-100`. See `docs/systems/embeds.md` for the bidirectional server-and-client contract.

When dimensions are not known (probe failed, no OG tags, non-image type), the renderer must rely on a structurally fixed layout (iframe with hardcoded height, fixed-size thumbnail) rather than a dimension-fallback wrapper. Fallback wrappers using a default `aspect-ratio` (e.g. 4/3) cause visible letterbox bars on content whose true ratio differs — that exact failure caused the revert in commit `0c84029`. The size and load handlers of the anchoring model absorb residual layout shift from un-reserved content.

Renderers known to satisfy the contract today:
- `AttachmentRenderer.tsx` — reserves from `attachment.width/height`.
- `embeds/ImageEmbed.tsx` — reserves from `embed.width/height` when populated.
- `embeds/VideoEmbed.tsx` — fixed 16:9 reservation for both branches: `aspectRatio: '16/9'` for the direct-video container, `paddingBottom: 56.25%` for the provider-iframe container.
- `embeds/RichEmbed.tsx` — explicit `height` from `getIframeHeight()`; fixed 80×80 thumbnail in collapsed state.
- `embeds/GenericEmbed.tsx` — fixed 80×80 thumbnail.

Renderers that do not reserve (residual shift, sentinel-covered):
- Bare GIF URLs in `Message.tsx` — Tenor/Klipy URLs are not embed records, no dims.
- Markdown inline images in `MarkdownRenderer.tsx` — `![](url)` syntax carries no dims.

## Known limitations

- Bare GIFs and markdown images shift on load. The ResizeObserver and load handlers re-apply the anchor, so the view stays on its anchor while they settle.
- The 150px at-bottom tolerance is generous — sending a new message while the user is reading the last few messages 100px up from the bottom yanks them down. This is intentional today; if changed, update this doc and the spec history.
- A user scroll in the same frame as a layout change is read as layout and re-anchored; the next scroll event moves the anchor.
- The smooth-scroll UX is preserved deliberately for both new-message arrival and Jump-to-Present per UX call. The 2026-04-27 fix (smooth-scroll intent + scrollend final pin) closes the residual above-bottom-landing race without removing the animation.

## Out of scope (deferred)

These items were considered and rejected for the 2026-04-25 work; they live here so their failure modes are findable when they actually occur:

- **Persisting `scrollPositions` across reloads.** Rejected — would silently hide new messages and confuse users returning to old context. Opening at the first unread message covers the cross-session case from the server's read state.
- **Tightening the 150px at-bottom tolerance.** Separate UX decision, not driven by any current bug.

- 2026-05-05 — sticky pagination skeleton on federated channels (parallel loadMessages/loadMoreMessages dedup): the 2026-05-05 hook + clamp-scroll fix above did not cover the federated-LAN reproduction. Playwright trace against the live deployment showed every channel mount firing TWO parallel `GET /channels/:id/messages?limit=50` requests, and every fast-scroll burst firing N parallel `loadMoreMessages` requests. Two cooperating root causes: (a) `AppLayout.tsx:289` AND `MessageList.tsx:267` both call `loadMessages(channelId)` in their channel-mount effects — `MessageList`'s call is required for surfaces that don't have the AppLayout chrome (`VoiceChatPanel`), so neither can be removed unilaterally; (b) `handleScroll`'s load-more block sees `!isLoadingMore` as true in every scroll event of a fast burst because all events share one closure created before the first `setIsLoadingMore(true)` commits. The chatStore guard `if (!force && get().hasMore.has(channelId)) return;` only deduplicates calls *after* the first completes — it does not collapse parallel callers. On a NAT hairpin'd LAN where some federated TCP connections succeed and others hang, having N hung parallel fetches per channel mount keeps `chatStore.isLoading` and component-level `isLoadingMore` true while any one of them is still waiting on the 30 s api-client timeout, producing the visually-stuck pagination skeleton across channel switches. Fix: in-flight Promise dedup at the chatStore level. `loadMessages` and `loadMoreMessages` each consult a module-level `Map<channelId, Promise>`; concurrent callers receive the same Promise. The map entry is cleared in a `finally` block, with a `inFlightLoads.get(channelId) === promise` self-check so a force-reload (WS reconnect) scheduled mid-flight isn't dropped. `force=true` callers bypass dedup intentionally — WS reconnect needs a fresh fetch even if a stale one is still pending. Net effect: one federated fetch per channel mount, one per fast-scroll burst, predictable timeout window, skeleton clears within ≤ 30 s + minDisplay even on full hairpin failure.
